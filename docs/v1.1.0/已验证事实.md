## 3. 用户管理已确认的问题（任务 3）

1. **访客额度前后端不一致**：后端 `GUEST_DAILY_QUOTA=3`（config.py:29）；前端 `renderIdentity` 显示“每日 5 张”，`applyRoleUi`(app.js:41) 又显示“每日 3 张”。
2. **`admin_update_user` legacy 额度映射混乱/有 bug**（main.py:1651-1669）：`resolution_1k/2k/4k` 旗标被同时套用到 image 和 video 两套额度；而 `image_quotas` 的键是 `2k/4k/6k/8k`（**没有 `1k`**），legacy 分支与新 `image_quotas/video_quotas` 字段重叠，语义含糊。
3. **改密码不失效其它会话**：`change_password`(main.py:830) 只更新 `password_hash`，不删除该用户其它 session（对比 admin 改密 1702 / 禁用 1685 会 `DELETE FROM sessions`）。
4. **`delete_account`(main.py:846)** 手写 `response.delete_cookie('superphoto_session', ...)` 而非复用 `clear_session`；风格不一致（功能上靠 users→sessions 的 `ON DELETE CASCADE` 兜底）。
5. `require_admin`(auth.py:114) 用字符串字面量 `'admin'` 而非 `ROLE_ADMIN` 常量。
6. `auth_me`(main.py:653) 内 `service_health()` 会再开一个 `connect()`（连接内套连接）。
7. 访客 `daily=3`、`active=2` 在 `usage_summary`(445-446)、`create_modern_batch`(1149-1150)、`retry_job`(1342) 等多处硬编码。
8. `get_session`(auth.py:63) 对每个匿名访客都建 session 行 → 会话膨胀（有 `cleanup_expired` 定时清理兜底）。

## 4. 异步逻辑已确认的问题（任务 4）

- 模型：`worker_loop` 用 `claim_job`（`BEGIN IMMEDIATE` + 租约）领取任务，心跳线程每 10s 续租，`LEASE_SECONDS=30`。崩溃后租约过期可被他人重领(`attempts<2`)，`publish_success` 有 `lease_owner` 归属校验兜底，不产生错误输出。
1. **图片任务无取消检查点**：`process_job`(285) 图片路径调用 `update_progress` 但**不检查返回值**（仅视频路径 246 检查）。`cancel_job`(1303) 把 processing 图片任务置 cancelled 并清 lease 后，worker 仍会算到底，再在 `publish_success`(361) 因 lease 不匹配丢弃——安全但浪费算力。
2. **`rate_limit`(main.py:161) 是进程内的**：`_rate_buckets` + 全局锁，多 uvicorn worker 下限流失效；空桶从不回收，有轻微内存增长。
3. **租约偏紧**：lease 30s / 心跳 10s，超大图或 DB 抢锁时若续租不及时会被重领并重复计算。
4. `claim_job` 里“单视频串行”子查询在移除视频后可整体删除。
- 取消语义安全性已核实：cancel 清 `lease_owner`，`finish_job`(73) 要求 `status='processing'`、`publish_success` 要求 `lease_owner` 匹配，二者都不会命中被取消的任务 → 不会误改状态。

## 5. Personal_Sub2 (Sub2API) 的 OIDC 能力（任务 2 前提，子智能体只读调研核实）

- 目录 `D:\Codex_Program\Personal_Sub2\main`，Go 后端 + 前端。
- **它同时具备两套独立实现**：
  - 作为**客户端(RP)** 去对接上游 IdP：`backend/internal/handler/auth_oidc_oauth.go` + `config.go:332 OIDCConnectConfig`（支持通用 OIDC、LinuxDO、微信、钉钉、邮箱验证码；支持 PKCE S256）。
  - 作为**服务端(OpenID Provider)** 对外签发：`backend/internal/server/routes/oidc_provider.go` 注册以下公开端点——
    - `GET /.well-known/openid-configuration`（Discovery）
    - `GET /oauth/authorize`、`GET/POST /oauth/login`、`GET/POST /oauth/consent`
    - `POST /oauth/token`、`GET/POST /oauth/userinfo`、`GET /oauth/jwks`、`POST /oauth/revoke`
- Discovery 声明（`oidc_provider_service.go:82-111`）：`response_types_supported=["code"]`、`grant_types_supported=[authorization_code, refresh_token]`、`id_token_signing_alg_values_supported=["RS256"]`、`code_challenge_methods_supported=["S256"]`、`token_endpoint_auth_methods_supported=["client_secret_basic"]`、`authorization_response_iss_parameter_supported=true`。
- 令牌：id_token 为 **RS256** 签名的 JWT（私钥 RSA-3072，AES-256-GCM 加密存库），access/refresh 为不透明随机串；id_token 按 scope 附 `preferred_username/email/role`。
- **两道启用门槛**（决定“开箱可用性”）：
  1. `oidc_provider.enabled` **默认关闭**（`config.go:362` 注释 disabled-by-default），且必须已激活一把签名密钥，否则端点 fail-closed（404/503）。
  2. Provider 端点被硬编码**只在 Host = `auth.taffy.edu.kg` 时响应**（`oidc_host.go:15`、`oidc_provider_config.go:10` 冻结 issuer 与 RS256/PKCE 契约）。
- 结论：SuperPhoto 走**标准 OIDC Authorization Code + PKCE，作为 confidential client**（token 端点用 HTTP Basic 传 client_id/secret）即可对接，端点用 discovery 自动发现。**但 Sub2 侧需先由用户完成运维配置**：①开 `enabled`、②生成/激活签名密钥（admin `POST /admin/oidc-provider/keys/rotate`）、③注册 SuperPhoto client（admin `POST /admin/oidc-provider/clients`，回调须 https）；若实际 issuer 域名 ≠ `auth.taffy.edu.kg`，需在 Sub2 解冻该常量（本项目范围外）。
